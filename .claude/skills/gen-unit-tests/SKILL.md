# gen-unit-tests

## Коли застосовувати
Нова або змінена функція в `core/`, `storage/` чи `api/` ще не має тестів, або тести неповні.

## Процедура
1. **Прочитати модуль** і перелічити публічні функції, їхні параметри, винятки й граничні випадки.
2. **Звернутися до бази знань** через MCP: `search_notes` за назвою модуля й пов'язаних понять, `get_note` для компонента та рішень (ADR). Правила предметної області (наприклад, інтервал у днях) брати з нотаток, а не вигадувати. Читати vault у обхід MCP заборонено (B-06).
3. **Перевірити guardrails** (`docs/guardrails.md`): створення файлів тестів – W-03 (потрібне підтвердження), зміна `core/` чи `storage/` – W-01; видалення файлів і push у `main` заборонені (B-01, B-02). За потреби дочекатися підтвердження людини.
4. **Написати тести** у `tests/test_<модуль>.py` за шаблоном:
   - імена `test_<функція>_<сценарій>`;
   - структура arrange / act / assert, один сценарій на тест;
   - `pytest.mark.parametrize` для граничних значень;
   - перевірка винятків через `pytest.raises` для некоректних даних;
   - БД лише тимчасова (`:memory:` або `tmp_path`), без мережі й без реальних даних.
5. **Запустити** `pytest -q` і `ruff check .`; виправити тести або повідомити про дефект у коді, якщо тест виявив помилку (код без запиту не змінювати).
6. **Сформувати результат** у форматі нижче.

## Формат результату
- Перелік покритих сценаріїв (звичайні, граничні, помилкові).
- Результат `pytest` (скільки пройшло) та `ruff`.
- Посилання на використані нотатки vault.
- Що потребує рішення людини (знайдені дефекти, неоднозначності).

## Пов'язані guardrails
W-01, W-03, B-01, B-02, B-06.
