# Handoff: planner → coder

## Задача
«Реалізувати нагадування про ревакцинацію: модуль, який за списком вакцинацій і поточною датою повертає вакцинації, ревакцинація яких настає в найближчі N днів. Граничні випадки визначити за базою знань і наявним кодом.»

## Що зроблено
Я прочитав інструкцію ролі, шаблон handoff і `docs/guardrails.md`. Потім вивчив код `core/vaccination_schedule.py`, `core/overdue.py`, `storage/repository.py` і тести `test_overdue.py`, `test_vaccination_schedule.py`. У vault через MCP знайшов і прочитав потрібні нотатки (перелік у розділі «Використані джерела»).

План:
- Новий модуль `core/upcoming.py` у шарі core, чиста функція без вводу-виводу.
- Він перевикористовує `VaccinationRecord` і `next_due_date`, а також правило «остання вакцинація для пари (тварина, вакцина)» з `core/overdue.py`.
- Нові тести лежать в `tests/test_upcoming.py`.
- Ні storage, ні api не чіпаємо.

## Рішення та обґрунтування

**1. Шар: `core/` (ADR-002).**
- Нотатка «Модуль графіка ревакцинації» і ADR-002 вимагають, щоб бізнес-логіка була в core без доступу до бази, тоді її можна тестувати окремо.
- Функція отримує `list[VaccinationRecord]` і `today` як аргументи. Читання з БД лишається за Repository, а виклик із HTTP API — справа майбутнього шару api (у vault він має `status: planned`).
- Дані власників (контакти для нагадувань) не потрібні. Модуль лише обчислює, кому й що нагадувати.
- Відкинуто: логіку в `storage/` (порушує напрямок залежностей api → core → storage) і метод у Repository зі SQL-фільтром за датою (дублює розрахунок із ADR-003).

**2. Файл: новий `core/upcoming.py`, а не розширення `overdue.py`.**
- Окремий файл зберігає єдину відповідальність модулів. Компонент «Модуль прострочених вакцинацій» описаний як модуль саме прострочень, і так само відповідає ФВ-6.
- Стиль беремо з `overdue.py`: `from __future__ import annotations`, `@dataclass(frozen=True)`, докстрінги українською, довжина рядка до 130 (ruff, правила E, F, I, B).

**3. Сигнатури.**
```python
@dataclass(frozen=True)
class UpcomingItem:
    animal_id: int
    vaccine: str
    due_on: date
    days_left: int          # 0 = ревакцинація сьогодні

def is_upcoming(due_on: date, today: date, days: int) -> bool: ...
def upcoming_revaccinations(records: list[VaccinationRecord], today: date, days: int) -> list[UpcomingItem]: ...
```
Паралель із `OverdueItem`, `is_overdue` і `overdue_vaccinations`: `today` передається явно, час усередині функцій не читається (детермінізм, як в існуючих тестах із `TODAY`).

**4. Дублювання логіки «остання вакцинація».**
- Рекомендація: винести з `overdue_vaccinations` цикл вибору останнього запису в публічну функцію `latest_records(records) -> list[VaccinationRecord]` у `core/overdue.py`.
- Поведінка `overdue_vaccinations` не змінюється, наявні тести `test_overdue.py` мають лишитися зеленими без правок.
- Якщо coder вважає рефакторинг ризикованим, допустима альтернатива: приватна копія логіки в `upcoming.py` з коментарем-посиланням на ADR-008. Тоді в handoff до reviewer треба зазначити дублювання.

**5. Граничні випадки.**

| Випадок | Рішення | Підстава |
|---|---|---|
| Вікно | Закрите з обох боків: `0 <= (due_on - today).days <= days`. | ADR-008: `due < today` означає прострочено, тому `due == today` не прострочена. Щоб не було «діри», такий запис має потрапляти в нагадування, а прострочені в нагадування не потрапляють. Множини прострочених і найближчих не перетинаються й разом покривають усі `due`. |
| Сьогодні (`due == today`) | Включати, `days_left = 0`. | ADR-008 |
| Рівно `today + N` | Включати. | Природне читання «в найближчі N днів»; зафіксувати тестом як рішення. |
| `today + N + 1` | Не включати. | — |
| Учора (`due < today`) | Не включати, це сфера `overdue.py`. | ADR-008 |
| `days == 0` | Допустимо: повертається лише `due == today`. | Випливає з закритого вікна. |
| `days < 0` | `ValueError`. | У vault правила немає. Мовчки повернути порожній список означало б приховати помилку виклику. |
| Остання вакцинація | Для кожної пари (animal_id, vaccine) бере лише останню. Свіжіша вакцинація знімає нагадування за старою. | ADR-008, `test_overdue_vaccinations_uses_latest_record_per_animal_and_vaccine` |
| Невідома вакцина | Пропускати `UnknownVaccineError` нагору, не ковтати. | ADR-007, і так само поводиться `overdue.py` через `next_due_date`. |
| Високосний день | Нічого додатково не робити, лише дні, а не роки. | ADR-003, `test_next_due_date_leap_day_uses_days_not_calendar_year` |
| Порожній вхід | Повертає `[]`. | Паралель із `test_overdue_vaccinations_empty_input`. |
| Сортування | За `(due_on, animal_id, vaccine)`: найближчі першими. | Узгоджено за змістом із `overdue.py`, де першим іде найстарше прострочення. |
| Переповнення дат | Не рахувати `today + timedelta(days)`, а порівнювати `delta = (due_on - today).days`. | Для великого N додавання до `date` кидає `OverflowError`, а різниця дат безпечна. |

**6. Відкинуті альтернативи.**
- Пільговий або «м'який» період: ADR-008 уже відкинув його як ускладнення без вимоги від користувача.
- Один «об'єднаний» статус (прострочено / незабаром) в одній функції: змішує дві чіткі функції й ламає прості контракти.
- Читання `today` усередині модуля: втрачається тестованість.

## Ризики й відкриті питання
- **Прогалина у vault.**
  - Пошук за формами «нагадування», «граничн», «вікно», «N днів», «майбутн» не знайшов жодного правила для вікна «найближчі N днів». Є лише ADR-008 про прострочення та згадка про нагадування в нотатці «Власник».
  - Закритість вікна (включно з `today` і `today + N`) і `ValueError` при `N < 0` є рішеннями planner, виведеними з ADR-008, а не готовими правилами. Їх варто зафіксувати новим ADR (див. нижче) і за потреби підтвердити в користувача.
- **У `docs/app-requirements.md` немає функціонального вимоги** під це нагадування (ФВ-1…ФВ-8). Запропонувати користувачу ФВ-9 і не додавати його без підтвердження (W-03).
- **Вакцинація в майбутньому** (`vaccinated_on > today`): у vault правила немає. Не обробляти спеціально, вона підпадає під загальне вікно. Це потенційно дивний вхід, його варто згадати у звіті, а не вигадувати поведінку.
- **Рефакторинг `overdue.py`** (пункт 4) зачіпає наявний модуль. Якщо тести `test_overdue.py` після нього хоч трохи змінюються, це сигнал відкотити рефакторинг і взяти альтернативу.
- **Hook за шляхом vault** спирається на підрядок `knowledge-base` у назві каталогу. Не обходити його непрямими способами (B-06).

## Що очікується від наступної ролі

**Файли.**
1. `core/upcoming.py` — новий модуль (`UpcomingItem`, `is_upcoming`, `upcoming_revaccinations`). Потребує підтвердження людини за W-01.
2. `core/overdue.py` — лише винесення публічної `latest_records` без зміни поведінки (W-01), якщо обрано рекомендований варіант.
3. `tests/test_upcoming.py` — нові тести (W-03). Імпорти й `TODAY = date(2026, 11, 6)` як у `test_overdue.py`.

**Тестові сценарії** (`pytest`, A-02).
- `is_upcoming` параметризовано за межами при `days=7`:
  - учора: False
  - сьогодні: True
  - `today+7`: True
  - `today+8`: False
- `days=0` повертає лише записи, що настають сьогодні.
- `days < 0` піднімає `ValueError`.
- Повертає лише записи у вікні, з правильними `due_on` і `days_left` (як у `test_overdue_vaccinations_returns_only_overdue`).
- Прострочені записи не входять до результату, а `due == today` входить з `days_left == 0`.
- Остання вакцинація для пари (тварина, вакцина): стара запис, що потрапила б у вікно, не повертається, якщо є свіжіший запис, чия дата виходить за вікно. І навпаки: свіжіший запис, що потрапляє у вікно, береться, а старий ні.
- Різні вакцини однієї тварини обробляються незалежно (наприклад «Сказ» і «Бордетела» з інтервалами 365 і 180 днів).
- Сортування за `due_on`, потім `animal_id`, потім `vaccine`.
- Невідома вакцина піднімає `UnknownVaccineError`.
- Високосний день: вакцинація 29.02.2024 «Сказ» → due 28.02.2025, перевірити потрапляння у вікно.
- Порожній список повертає `[]`.
- Дуже великий `days` (наприклад 10**9) не падає з `OverflowError` і повертає всі майбутні записи.
- Якщо виконано пункт 4: `latest_records` має мати власний тест, а весь `test_overdue.py` проходить без змін.

**Критерії готовності.**
- `pytest` і `ruff check` без помилок.
- Жодних змін у `storage/`, `api/` і vault (запис у vault потребує W-05 і виконується окремим кроком, після схвалення).
- У handoff до reviewer перелічено, які рішення виведені з vault, а які є власними (закритість вікна, `ValueError`, сортування).

**Нотатки vault, які варто створити або оновити після змін** (через MCP, W-05, лише з підтвердженням):
- новий ADR-010 «Вікно нагадувань про ревакцинацію» із фіксацією рішень таблиці вище;
- нова нотатка-компонент «Модуль нагадувань про ревакцинацію» (`path: core/upcoming.py`, `layer: core`, `depends_on` на «Модуль графіка ревакцинації» і «Модуль прострочених вакцинацій»);
- оновити «Ревакцинація» посиланням на нагадування, а `MOC-Застосунок` переліком нових нотаток.
